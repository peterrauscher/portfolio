AI agents are awkward Kubernetes workloads. A worker can spend most of its time waiting on an LLM, a browser, or an external API while using almost no CPU. When a burst of work arrives, the CPU graph can look perfectly healthy while the queue gets longer and users wait.

For this kind of worker, I would rather scale from work waiting than from CPU usage.

[KEDA](https://keda.sh/) is a good fit. It watches an event source such as Redis, Kafka, RabbitMQ, or SQS and turns that signal into a Kubernetes scaling decision. The basic setup is:

1. Put agent tasks in a durable queue.
2. Run a worker Deployment that claims one task at a time.
3. Scale the Deployment from the queue depth.
4. Put a ceiling on replicas so a traffic spike does not become a token-spending spike.

Before touching the `ScaledObject`, decide what one task means. That boundary matters more than the YAML.

## Give each worker a bounded task

A worker should not hold an entire conversation or workflow forever. It should claim a task, do one bounded piece of work, save the result, and return to the queue.

A task might look like this:

```json
{
  "id": "task_123",
  "workflow": "support-ticket",
  "input": {
    "ticketId": "ticket_456"
  },
  "attempt": 1,
  "createdAt": "2026-08-06T12:00:00Z"
}
```

The worker needs a lease or visibility timeout. Otherwise a crashed pod can remove a task permanently. It also needs idempotency. If the same task is delivered twice, the second attempt should not send a duplicate email, charge a card twice, or overwrite a newer result.

KEDA can add pods. It cannot decide whether those pods are safe to run in parallel. That is a queue and worker problem.

## A small agent worker Deployment

Here is a deliberately boring Deployment. It has no HTTP endpoint. It waits for work, claims a task, and runs the agent loop.

```yaml title="agent-worker.yaml"
apiVersion: apps/v1
kind: Deployment
metadata:
  name: agent-worker
spec:
  replicas: 0
  selector:
    matchLabels:
      app: agent-worker
  template:
    metadata:
      labels:
        app: agent-worker
    spec:
      terminationGracePeriodSeconds: 90
      containers:
        - name: worker
          image: ghcr.io/example/agent-worker:2026-08-06
          env:
            - name: REDIS_HOST
              value: redis.default.svc.cluster.local
            - name: REDIS_PORT
              value: "6379"
            - name: AGENT_QUEUE
              value: agent-tasks
            - name: MAX_TASK_DURATION_SECONDS
              value: "300"
          resources:
            requests:
              cpu: 100m
              memory: 256Mi
            limits:
              memory: 1Gi
```

`replicas: 0` is intentional. KEDA can wake the Deployment when the queue becomes active. If the agent loads a large local model, or if startup is slow, use `minReplicaCount: 1` and keep one worker warm.

The termination grace period is there for the same reason. Agent tasks often spend more time waiting on an API than doing compute. Give the worker enough time to finish or release its lease when Kubernetes asks it to stop.

## Scale from Redis queue depth

KEDA's Redis Lists scaler uses the list length as its signal. The `listLength` value is a target queue depth per replica. It is not a command to create one pod for every item in the list.

```yaml title="agent-worker-scaledobject.yaml"
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: agent-worker
spec:
  scaleTargetRef:
    name: agent-worker
  pollingInterval: 15
  cooldownPeriod: 180
  minReplicaCount: 0
  maxReplicaCount: 24
  triggers:
    - type: redis
      metadata:
        hostFromEnv: REDIS_HOST
        portFromEnv: REDIS_PORT
        listName: agent-tasks
        listLength: "2"
        activationListLength: "1"
      authenticationRef:
        name: agent-worker-redis
```

This example checks Redis every 15 seconds, aims for about two queued tasks per active worker, and caps the Deployment at 24 replicas. When the list is empty, KEDA can eventually take the worker count back to zero. The cooldown keeps a brief gap between tasks from immediately removing every warm worker.

Keep Redis credentials in a Kubernetes Secret or an external secret manager. A `TriggerAuthentication` maps the password to the scaler without putting it in the `ScaledObject`:

```yaml title="agent-worker-auth.yaml"
apiVersion: keda.sh/v1alpha1
kind: TriggerAuthentication
metadata:
  name: agent-worker-redis
spec:
  secretTargetRef:
    - parameter: password
      name: redis-credentials
      key: password
```

Redis Lists are convenient for the example, but the same idea works with the queue you already operate. The delivery semantics matter more than the scaler name. At-least-once delivery is common, so retries and deduplication belong in the worker.

## Pick a target from latency

A queue-depth target only means something when it reflects the latency you want.

Suppose one worker completes two tasks per minute and you want a 30-second queue wait. A target of two might be reasonable. If each task takes five minutes, that target is far too high. With highly variable task durations, average queue length hides the slow tail. Queue age may be the better signal.

I would start with this rough model:

```text
required workers = ceil(arriving tasks per minute × average task duration in minutes)
```

Then I would test it with real workloads. The useful measurements are queue depth, oldest-task age, time to claim a task, task duration, retry rate, active model requests, token throughput, provider rate limits, and worker startup time.

The pod count is not the goal. I care about task latency that stays predictable without blowing through the model budget.

## Put a budget around the cluster

A queue can grow faster than an LLM provider can serve requests. Without a cap, autoscaling turns a traffic spike into a token-spending spike and then into a rate-limit storm.

`maxReplicaCount` is the first guardrail. I would also:

- limit in-flight model calls per worker
- use a shared rate limiter for each model and organization
- give each task a deadline and retry budget
- reserve capacity for high-priority queues
- stop accepting work when queue age passes the SLO
- track estimated and actual token usage by workflow

Different workloads deserve different pools. A browser-heavy research agent and a short classification agent will have different memory needs, task durations, and safe concurrency. Putting both in one Deployment hides those differences from the autoscaler.

## The node pool still matters

KEDA changes the desired replica count. Kubernetes still needs somewhere to place the pods.

If the node pool is full, the queue can keep growing while the Deployment reports unschedulable pods. Pair the worker autoscaler with a node autoscaler, or keep enough headroom for the burst you actually expect. GPU workers need especially careful planning because one pending pod may require an entire GPU-shaped node.

I would monitor the whole chain:

```text
queue grows → KEDA observes it → HPA requests replicas → scheduler places pods → workers claim tasks
```

Queue depth alone will not tell you where the failure is. Watch oldest-task age, pending pods, worker readiness, and completed tasks too.

## Scale-to-zero costs latency

Scale-to-zero is useful for spiky asynchronous work. It also adds a cold start.

When the first task arrives, KEDA has to observe it, Kubernetes has to schedule a pod, the image has to start, and the worker may need to connect to dependencies or load a model. All of that counts against the task's latency.

Use zero replicas when a few extra seconds are acceptable. Keep one warm worker when the queue backs a synchronous request, startup is expensive, or the worker's cache is worth keeping around.

## Keep state outside the pod

A pod is disposable. I would not keep any of these as the source of truth inside it:

- conversation history
- tool results
- workflow state
- task leases
- partial outputs
- retry counts

Put them in a database or workflow system. A worker should be able to disappear after claiming a task and have another worker resume or retry it safely. The pod is just the process doing the work, not the record of what happened.

## Where to start

Start with one queue and one worker Deployment. Give the worker a bounded task contract, make side effects idempotent, and measure queue age before tuning replica counts. Then add the `ScaledObject` with a conservative `maxReplicaCount`. Keep one warm worker until the cold-start path has real measurements behind it.

The KEDA configuration is the easy part. The queue contract, task lifecycle, model budget, and backpressure rules decide whether an agent cluster is safe to scale.

For the full set of fields and scaler options, see the [KEDA ScaledObject specification](https://keda.sh/docs/latest/reference/scaledobject-spec/) and the [Redis Lists scaler documentation](https://keda.sh/docs/latest/scalers/redis-lists/).
